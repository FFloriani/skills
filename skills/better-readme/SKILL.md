# README de GitHub que as pessoas entendem

Quem usa esta skill publica um projeto no GitHub e não sabe documentar. O resultado tem que responder, para um estranho e em poucos segundos: **o que é, que dor resolve, como obter e como usar**, sem inventar nada. Fala com o usuário em linguagem simples, sem aula: uma linha de motivo por decisão.

A base é um estudo de guias oficiais (GitHub Docs, standard-readme, makeareadme, Write the Docs, Google), de estudos empíricos (Prana et al. e outros) e de 36 READMEs reais. O que é **regra** (mecânica do GitHub) fica separado do que é **boa prática** (sem estudo de efeito).

## Regras que não mudam

1. **Fato antes de texto.** Cada comando, versão, link, requisito e funcionalidade vem de algo que você leu no repositório ou que o usuário disse. Sem rastro, não entra: vira `<!-- PENDENTE: ... -->` e vai para a lista final.
2. **Responder primeiro, enfeitar depois.** A primeira tela diz o que é, para quem e como obter. Badge, apoio, merch, créditos e história vêm depois.
3. **Esqueleto pelo tipo do projeto.** Não existe modelo único (`references/esqueletos.md`).
4. **Regra versus boa prática.** Mecânica do GitHub (onde o arquivo vive, o que o renderizador remove, limites) é regra. Número de badges, tamanho, posição do apoio, emoji, diagrama são boa prática: sugira com o motivo, aceite recusa e **nunca prometa** que isso aumenta estrelas, adoção ou contribuição (nenhum estudo mostra).
5. **Pouco e informativo.** 3 a 5 badges que respondem a uma pergunta real; sem emoji decorativo; sem adjetivo de marketing nem texto com cara de IA.
6. **Nada que envelhece.** Sem contagem fixa de estrelas, downloads ou versão escrita à mão; use badge dinâmico ou o link `latest`.
7. **Nunca** sobrescreva um README existente sem confirmar. **Nunca** invente canal de apoio, chave Pix, e-mail, assinatura de código nem a promessa "portátil".
8. **Publicar é do usuário.** Escreva os arquivos; não faça commit, push nem altere About, topics ou social preview do repositório sem pedido explícito. Entregue o texto pronto.

## Fluxo

### 0. Modo

Pelo pedido (ou pelo argumento: `/better-readme auditar`, `criar`, `melhorar`, `traduzir`, `download`, `apoio`):

| Modo | Quando | Saída |
|---|---|---|
| **criar** | Não existe README | README novo |
| **melhorar** | Existe e o usuário quer reescrever | README novo preservando o que é fato do autor |
| **auditar** | "revisa", "o que está errado" | Relatório P0/P1/P2, sem alterar arquivo |
| **traduzir** | Já existe README e pede outro idioma | `README.<tag>.md` + seletor nos dois |
| **módulo** | Só download, só apoio/FUNDING.yml, só idiomas | O módulo, sem reescrever o resto |

Se existe README e o pedido não diz o que fazer, pergunte: **sobrescrever, mesclar ou só auditar?** Se o README tem sinais de gerador (`readme-ai`, "generated by"), avise que a edição certa é no gerador.

### 1. Descobrir (não pergunte o que o repositório responde)

```bash
python "<pasta-da-skill>/scripts/descobrir_fatos.py" "<pasta do projeto>"
```

Devolve JSON: git (owner/repo, branch, tags), manifestos, **tipo provável com evidências**, licença, README atual, mídia existente, workflows e releases, arquivos de comunidade, FUNDING.yml, READMEs traduzidos e sinais de "portátil". Depois **leia o que o script não lê**: ponto de entrada, `--help` ou comandos registrados, `examples/`, `tests/` e workflows de release, para as funcionalidades e os nomes reais de asset. Se houver `gh`, use `gh repo view` e `gh release list`.

Monte o **registro de fatos**: lista curta `fato | onde achei`. Tudo que entrar no README deve estar nela.

### 2. Perguntar (até 5 por rodada, só o que o repositório não revela)

Agrupe numa única mensagem curta, com uma sugestão de resposta padrão em cada uma:

1. **Para quem é e que dor resolve**, numa frase sua? (a intenção não está no código)
2. **O que o projeto não faz** e que alternativas você conhece?
3. **Idioma e público**: só Brasil, internacional ou ambos?
4. Tem **screenshot, GIF ou vídeo**, ou deixo marcador? (a skill não captura tela)
5. Quer **seção de apoio**? Quais canais você tem de verdade (Sponsors aprovado, Ko-fi, Pix)?

Só quando a busca for inconclusiva: o executável é assinado? o portátil não grava fora da pasta? aceita contribuição? qual o status (ativo, manutenção, experimental, arquivado)? qual o contato para suporte? (jogo ou mod) qual versão do jogo foi testada e qual a situação de afiliação? Se o usuário já respondeu, não repita. Se ele quer só rapidez, use as sugestões padrão e liste as suposições no final.

### 3. Escolher esqueleto e módulos

Pelo `tipo_provavel` (confirme se a confiança for baixa) abra `references/esqueletos.md` e escolha: biblioteca, CLI, app desktop (inclui jogo e mod), API, extensão, lista awesome, template, tutorial, perfil ou só documentação. Módulos opcionais: **Baixar** (releases e portátil), **Apoio**, **Idiomas**, **Diagrama**, **Comparação**, **Solução de problemas**.

### 4. Redigir

Siga `references/redacao.md`: frase de definição de até 120 caracteres (igual ao About e ao manifesto), "Por que existe" em 3 a 5 linhas com limite honesto, funcionalidades por benefício com rastro no código, início rápido copiável de até ~15 linhas com a saída esperada, instalação por gerenciador só do que existe. Tom direto, termos da interface exatos, sem marketing.

### 5. Mídia e diagramas

Siga `references/github-markdown.md`: caminho relativo com a caixa exata, alt descritivo, `width`, `<picture>` para tema claro/escuro, alertas (no máximo 2), `<details>` para conteúdo secundário. Mermaid só com 3 ou mais componentes, em tipo clássico e com equivalente em texto. Vídeo: marcador para a URL gerada pelo editor do GitHub, ou GIF curto. Demo de CLI: arquivo `.tape` do VHS. O que o GitHub remove (`style`, `class`, `<svg>` inline, `<center>`, `<iframe>`, `<script>`) nunca entra.

### 6. Módulos Baixar, Apoio e Idiomas

Siga `references/download-apoio-idiomas.md`:

- **Baixar**: tabela com instalador e portátil, links `releases/latest/download/<asset>` com **nomes reais**, checksum, `<details>` do SmartScreen se não assinado, requisito de runtime em destaque, winget/scoop só se existirem. Portátil só com confirmação no código.
- **Apoio**: `.github/FUNDING.yml` só com chaves documentadas e seção curta perto do fim, **depois** de definição e download. Pix: o usuário fornece a chave; você nunca inventa.
- **Idiomas**: `README.md` + `README.<tag>.md`, seletor idêntico no topo de todos, comandos literais, marca de sincronização.

### 7. Validar (obrigatório antes de entregar)

```bash
python "<pasta-da-skill>/scripts/auditar_readme.py" README.md --tipo <app|jogo|mod|cli|biblioteca|api|awesome|extensao>
```

Corrija todos os **P0** e os **P1** razoáveis e rode de novo. Não entregue com P0. Depois faça a **leitura humana** de `references/auditoria.md` (o que o script não vê): a definição é clara? cada promessa tem rastro? o início rápido funciona? os nomes de asset batem?

Marcadores `<!-- PENDENTE: ... -->` (screenshot, vídeo, chave Pix) são esperados no rascunho: o script os lista à parte, e eles vão para a lista final.

### 8. Entregar

Resuma em poucas linhas:

- **Arquivos escritos** (README, `README.<tag>.md`, `.github/FUNDING.yml`, imagens).
- **O que você precisa fornecer** (a lista de PENDENTE: screenshot, GIF, chave Pix, assinatura de executável, release com os assets).
- **Texto pronto para o repositório** (não aplicado): About (= a frase de definição), topics (até 20, minúsculas) e social preview 1280×640.
- **Suposições** feitas por falta de resposta.
- Resultado da auditoria (P0 0, P1/P2 restantes) e o que ficou sem checar.

Não faça commit nem push, a menos que o usuário peça.

## Modo auditar

Rode `auditar_readme.py`, faça a leitura humana e entregue: veredito em uma linha, P0, P1 e P2 em tabela com a correção, o que não deu para checar e um próximo passo. **Não altere arquivo.** Detalhes em `references/auditoria.md`.

## Quando algo não cabe

- Projeto sem manifesto nem sinais claros: `tipo_provavel` vem `desconhecido`. Pergunte o que é; não adivinhe.
- Projeto de jogo ou mod: o esqueleto de compatibilidade e aviso legal é extrapolação (nenhuma fonte estudada cobre README de jogo). Diga isso ao usuário e peça as versões testadas.
- README que também sai em PyPI ou npm: imagens por URL absoluta, sem sintaxe só do GitHub.
- O usuário pede efeito ("para ganhar estrelas"): diga uma vez, sem sermão, que nenhum estudo mostra README causando estrelas, e foque em clareza para quem chega.
- Não sabe como o GitHub se comporta num caso (ex.: `latest/download` com pré-lançamento): diga e verifique no repositório antes de prometer.

- `references/download-apoio-idiomas.md`: releases e portátil, FUNDING.yml, Pix, idiomas, arquivos de comunidade.
- `references/auditoria.md`: P0/P1/P2, revisão humana, relatório, boa prática × regra.
- `scripts/descobrir_fatos.py`: registro de fatos do repositório (JSON).
- `scripts/auditar_readme.py`: checagens mecânicas P0/P1/P2.
- `evals/casos-de-teste.md`: casos para conferir o comportamento depois de mudanças.
