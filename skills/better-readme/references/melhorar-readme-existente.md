# Melhorar um README que já existe

Vale para os modos **melhorar**, **traduzir** e **auditar** quando já há README. Ideias de funil, mistura de públicos e pré-voo vieram, em grande parte, de práticas descritas na skill `better-readme` de tommy0103 (baseada no *Art of README*), reescritas aqui.

## Pré-voo: antes de editar qualquer coisa

1. **Árvore de trabalho.** `git status`. Com alterações não commitadas, o README pode carregar trabalho do autor: **não sobrescreva**. Escreva numa cópia (`README.novo.md`) ou numa worktree separada e mostre o diff, ou peça que o autor commite antes. `descobrir_fatos.py` mostra `git.sujo` e `arquivos_alterados`.
2. **Compare com o remoto.** README muda entre branches. `git fetch` e `git diff origin/<padrão> -- README.md`. Reescreva a partir do que o remoto diz hoje, não só do que está no checkout. O script mostra `commits_a_frente_do_remoto` e `commits_atras_do_remoto`.
3. **Procure o que fixa o texto.** Testes, CI e automações às vezes exigem títulos exatos, lista de arquivos ou frases. O script lista em `readme_citado_em_testes_ou_ci`. Se houver, reestruture o **teste** para afirmar o requisito (ex.: "existe um link para a licença", "Instalação vem antes de Contribuir"), não o formato (título exato). Escreva a justificativa da mudança para a descrição do PR. Nunca enfraqueça um teste em silêncio para a documentação passar.
4. **Documentos derivados.** README de pacote em subpasta, cópia no site, `docs/index.md`, descrição publicada em PyPI/npm. O script lista `possiveis_documentos_derivados`. Atualize junto ou registre como fora de escopo, de propósito.
5. **Gerador.** Se o README é gerado (`readme-ai`, "generated by"), edite o gerador e regenere; mudança à mão se perde.
6. **Pergunte** o que fazer, se o pedido não disse: **sobrescrever, mesclar ou só auditar**.

## Diagnóstico: modos de falha de README antigo

Leia o arquivo de cima a baixo como alguém que nunca viu o projeto. Os problemas mais comuns:

| Falha | Como aparece | Correção |
|---|---|---|
| **Públicos misturados** | Runbook de release, tabela de secrets do CI, árvore do repositório, guia de debug no meio do que o usuário lê. É a falha mais comum e a que mais prejudica. | Mover para `CONTRIBUTING.md` ou `docs/` e deixar um link (`conteudo-de-mantenedor` no auditor) |
| **Funil colapsado** | Detalhe interno nas primeiras 50 linhas, antes de o leitor saber se a ferramenta é para ele | Definição, prova visual e caminho para obter primeiro; detalhe depois |
| **Duplicação** | O mesmo fato (versão do runtime, comando de instalação) dito duas ou três vezes | Um lar por fato: no ponto mais raso em que o leitor precisa; linke o resto (`fato-repetido`, `bloco-repetido`) |
| **Enquadramento de uma ferramenta só** | Tabela escrita quando só havia um suporte, ainda abrindo com os detalhes dele depois de dez | Reescreva neutro e **confira no código**: o texto antigo pode estar errado (entradas faltando, semântica antiga) |
| **Defasagem** | Link relativo morto, faixa de versões que não bate, arquivo citado que foi apagado | Reconferir contra `git log` e o código (`link-quebrado`, `versao-fixa`) |
| **API sem link** | Existe referência detalhada no repo, o README nunca a linka | Adicionar o link na seção de uso |

## Regras de reescrita

- **Só conteúdo do usuário, em ordem de funil.** Conteúdo de mantenedor **move**, não é apagado.
- **Um lar por fato.** O que foi para a referência, linke; não resuma de novo por extenso.
- **Uso = a forma real da interação** (comandos, prompts, código), copiável. CLI: mostre a invocação **com a saída**.
- **Tabela para detalhe denso** (o leitor reconhece padrão em tabela mais rápido que em prosa); a versão em prosa vai para a referência.
- **Reverifique toda afirmação** contra o código antes de carregá-la para o texto novo. Nunca herde por fé.
- **Preserve o que é do autor**: história, agradecimentos, tom, exemplos próprios, a não ser que seja P0.
- **A preferência do autor vence o checklist, exceto em P0.** Enfeite que o autor gosta (gráfico de star history, badges, logotipo, emoji no seu estilo) fica, a menos que ele concorde em cortar. Pergunte antes de remover algo puramente decorativo. O checklist serve ao autor, não o contrário. Segredo exposto, link quebrado, promessa falsa e licença ausente **não** são preferência.
- **Licença copyleft ou restritiva** (AGPL, GPL, SSPL, BUSL, uso não comercial): uma linha ou badge nas primeiras 40 linhas; o texto completo fica no fim. Incompatibilidade de licença é o que desqualifica mais rápido.
- **Imagem que carrega informação crítica** fica no repositório, não em host externo: o README sobrevive ao host.

## Verificação antes de entregar

1. Todo link relativo e asset resolve (`auditar_readme.py`).
2. Rode **todo** teste que lê o README ou o CONTRIBUTING, não só a suíte que você acha que importa.
3. Releia como estranho, de cima a baixo, e anote onde você desistiria. Se os pontos de desistência vêm na ordem errada, o funil está errado.

## Entrega como lista de decisões

Um diff de prosa é difícil de aprovar; uma lista de decisões é fácil. Entregue:

```markdown
## O que mudou no README

- **Moveu:** <o que saiu do README e para onde foi> (ex.: "Release process" → CONTRIBUTING.md, com link)
- **Removeu e por quê:** <item> (ex.: duplicava o comando de instalação da linha 9)
- **Reescreveu:** <seção> (ex.: definição agora é "<...>"; antes só havia adjetivos)
- **Manteve por preferência sua:** <item decorativo que você quis manter>
- **Testes ou CI alterados:** <asserção antiga → nova, e por quê>, ou "nenhum"
- **Pendências para você:** <screenshot, chave, release...>
```
